# 员工目录与历史身份核查

适用于本次涉及员工选择、业务名单、账号绑定、身份迁移或历史错绑的工作。普通无名单页面不需要新增目录；既有 2.4/2.5 系统不因 Skill 更新强制改版或部署。

## 身份与业务名单

- SaaS 主责提供同企业可信稳定用户 ID、显示元数据、当前员工授权与受控目录。子系统保存该 ID 及参与、分组、任期等业务状态，不创建第二套员工账号或用姓名推断归属；名单存在本身不产生登录、页面或 Action 权限。
- 本人业务操作始终取可信 SSO/Action 的 `sub`；客户端的姓名、`userId` 或任选名单记录不是身份凭据。显示名可空，不得成为获权本人操作的必填或禁用条件。
- 负责人等被选员工与当前操作者分别记录；`createdBy`/审批人不能用选人或手填字段冒充。外部联系人和历史署名可保留业务文本，但不得用于员工鉴权、归属或个人统计。真实参与资格与 SaaS 权限分开判断；完整入口、浏览器和人员关系验收见 [统一身份验收](identity-acceptance.md)。
- 管理员为他人新增名单、分配员工或重新绑定时，必须从平台目录选择；禁止提供手输任意平台 ID 的绑定入口。服务端仍把选中 ID 当待验证输入，写入前再次 `resolve`，不得信任浏览器传来的姓名、部门、`verified=true` 或过期搜索结果。获权员工按业务规则为本人首次报名时直接使用可信 `sub`，不要求再选自己或调用目录，不因此认领任何未核实的历史记录。
- 普通业务名单编辑不得重新归属已有个人业务记录；历史错绑用下方专门核查流程。纯停用或移出已绑定成员可按自身业务授权办理，不因目标员工已停用而强制重新绑定；不能借这个例外新增目标、转移记录或扩权。

## 受控目录接口

先通过 Runtime 的 `platform-capabilities` 核对 `features.employeeDirectory`：`supported:true`、`version:1`、`authentication:"subsystem-sso-client-and-current-employee"`、`targetActiveOnly:true`，以及下方两个固定 endpoint。缺失或未知不算支持；只有实际 SaaS 发布验证后才能宣称可用。此服务端能力不使用浏览器 Bridge，也不要求额外全局前端控件。

需要选人的具体 create/update Action 可声明 `employeeDirectory:true`，不允许公开读取 Action 使用。不自动给所有 CRUD 开启，不凭声明新增员工授权。平台按该 Action 的当前数据范围筛选目标；显示名不是查询结果唯一键，同名仍以 `user_id` 区分。

后端向 Runtime 注入的固定 SaaS origin 请求，使用专用 `zjss_` 凭据；浏览器不得持有该凭据。保持 2.4/2.5，旧系统使用已支持的身份校验链，不为此单独迁移接入版本。

| POST 路径 | 参数 |
| --- | --- |
| `/api/v1/subsystem-sso/employees/search` | 当前可信 `user_id`、`auth_epoch`、`module_key`、`page_key`、`action_key`，以及 `query`（最多 100 字符）、`offset`（0..10000）、`limit`（1..50） |
| `/api/v1/subsystem-sso/employees/resolve` | 同一可信身份与 Action 上下文，以及 `user_ids`（1..100 个不重复 UUID） |

两种响应均包含 `organization_id`、`application_id`、`module_key`、`page_key`、`action_key` 与 `employees`；每位员工只含 `user_id`、`username`、可空 `display_name`。搜索另含 `has_more` 和可空 `next_offset`；解析必须返回精确相同的 ID 集合，不能接受缺项、多项或重复项。应用 ID 与可信 SSO 换码结果/Action claims 的 `applicationId` 比对，缺失时重新打开模块，不从浏览器补值；旧的普通登录和 Action 不因此拒绝。

平台目标必须属于同企业、未删除、启用且位于当前 Action 的有效范围。目标仍待首次改密不等于禁用；当前操作者的改密、停用、撤权和会话失效仍受平台限制。无目标、跨企业或超范围的解析统一返回 404。超时、能力缺失、错误响应不能退回姓名匹配、任意 ID 输入或缓存授权。

模板提供 `platform_employee_directory(actor, module_key, page_key, action_key, ...)` 和 `/api/ui/employees/search`，后者只从服务器会话取操作者。业务保存服务在同一授权流程中传 `user_ids` 精确重验后，再以返回 ID 创建参与记录；页面和 AI 共用该服务。模板不默认创建名单业务表或开启目录 Action。

## 历史全量核查与修复

身份修复或名单导入任务须盘点同一受影响名单/来源批次的全部成员，不只修用户指出的几人；范围以问题来源和实际关系为依据，不要求无关样式任务核查全企业。总数分为已核实、待确认、冲突、无可用账号并对账；同名只能生成候选，不能算核实证据。

先从业务 schema、查询与写入链查清全部引用，包括无外键的旧 ID/字符串引用、打卡、积分来源、调整明细、班委或负责人、任期分组、事件和导出快照。名单主表为零关联不等于没有业务引用。保存受控核查清单：旧身份引用、明确稳定目标 ID、权威证据引用、每类关联数量、冲突与待办；个人明细不放公共 Skill、Git、日志或公开交接。

盘点后区分活跃身份引用、不可变事件/幂等回执与历史展示快照。需要纠正的是已核实的活动归属关系，不是把全部旧 ID 字符串清零；不得改写签名内容、已消费确认或历史回执来伪造新的操作者。保留项及原因也计入对账。

已核实项先备份，再以旧值、目标未占用、关联数量/版本和证据版本为前置条件执行事务。跨表身份引用按明确映射一起处理；出现他人的记录、目标冲突、新增关联或预检后变化立即停止，不能逐表留下半修状态。无法证明归属的项保持待确认及隔离，用户授权修复不等于授权猜测。

历史姓名、分组等业务快照保持原样；积分金额、来源类型、日期和已发生业务事实不因纠正账号改变。需要修正快照或分数必须有独立业务依据和授权。本轮修复前后核对总记录数、各类关联数、积分汇总及快照摘要；记录已修、未修和原因。异常回滚与重复执行不应重复业务事件、补打卡或改分。

## 可执行验收

使用隔离数据执行真实身份函数、API 和数据库服务：无显示名仍能本人提交，伪造姓名/ID不能换归属；同名不合并，未声明 Action、撤权、跨范围与目录故障失败关闭；选择后目标停用/移出范围须在保存时被拒绝，已有成员纯退出按业务授权可办。

历史修复测试包含主表之外的旧 ID 引用、积分来源、目标已占用、关联数变化、混合待确认项、事务中途异常与重复执行，并回读记录数量、积分和快照。文档字符串、Manifest Schema 或 mock 成功响应只能验证各自边界，不能代替业务写入与历史关联测试。

分别报告模板合成测试、业务实际回读、浏览器双端与真实员工操作；不得替真实员工打卡。新增公共能力的依赖顺序是 SaaS 能力验证、Skill 稳定包、需要适配的子系统各自发布；已部署验证的能力和已发布契约直接复用，不要求每次业务修复重发 SaaS 或 Skill。规范更新不证明其他系统已经接入或历史数据已修复。
