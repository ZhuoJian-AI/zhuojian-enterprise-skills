# 现有系统定位与自主修复

适用于接手旧项目、功能修复、代码已改而用户看不到、导入或同步异常。以下是帮助判断的证据来源，AI 根据当前问题自行选择与组合，不要求按固定顺序执行全部检查。

## 线索与判断

目标是知道用户实际打开了什么，以及它依赖哪份代码、配置和数据。已有访问档案、服务器项目 AGENTS/README、Git 分支与改动、服务启动参数、反向代理、发布器和真实用户页面可以相互核对。根目录没有 subsystem.json 不等于不存在系统；可能在 direct-integration 等子目录。副本、预览目录和开发工作树也不天然等于当前生产源。

标准 Runtime 与旧专用发布器可以同时存在。`doctor` 可用时能提供诊断；命令无执行权、配置 PermissionError、服务自己的 runtimeInitialized=false 和平台未登记是不同事实。用已有获权资料或明确的主机选择器继续调查，不绕过权限，不因一次读取失败要求小白重做初始化。新接入基础缺失确实阻碍任务时，再说明具体依赖与可完成部分。

发布前选择实际当前源码，保留其他人的修改和已存在的运行方式。运行进程、冻结版本指针、配置引用及实际数据库比目录名更可靠；名为 acceptance/test 的配置也可能承载真实业务，不能据此清库、替换或迁移。备份按本次持久数据影响确定，不强制普通修改新增 OSS 或备份服务。

## 常见问题的证据

- 代码已改但页面没变：比较当前进程/制品与候选代码，实际页面脚本与缓存，以及 SaaS 加载的入口；不要让负责人反复刷新代替定位。
- “没同步”：查看实际 Manifest、同步回执及生效目录，区分健康接口成功、登记请求成功和平台接受新版本。`aiSemantics.relatedPages` 等字段按现役协议校验，不靠手写近似 JSON。
- 看不到界面：核对实际账号与企业、平台入口签发、SSO 换码、来源、业务关联和当前授权。平台有角色不证明旧系统的业务映射已接好，也不授权自动给所有人扩权。
- 导入按钮不可用：核对本人视角、前端分支/禁用逻辑、服务端精确能力与数据范围，再验证本次允许的业务结果；绕开按钮不等于修好流程。

技术工作由 AI 在现有授权内推进，保留用户业务规则。修一个故障不自动迁移协议、重写整个系统或新增其他通道。没有权限的部分说明具体缺口，已有权限内的调查和实现继续做。

## 如何判断完成

把本次承诺和证据对应：源码、当前运行版本、平台同步、真实用户结果分别说明。`e2e_acceptance.py` 的 pre_registration_only、拒绝探针或健康200不能当作本人成功办理。选择能验证受影响行为的方法；写入/外部发送仍按本次业务授权，未获权时采用已有记录、只读验证或隔离数据并明确未测。资料或 Skill 已更新不能代表业务已修好。
