# 统一身份的入口核查与验收

新建、接入旧系统、修改登录/权限/员工归属或修复身份问题时必读；普通样式维护只增量核对受影响入口，不要求无关数据全量迁移。此规范约束实现与交付，不增加 Manifest 字段、不替代 SaaS 实时权限，也不授权自动更改现有系统。

## 开工先查实际入口

从当前服务路由、反向代理与运行配置列出员工能访问的业务入口：独立页、iframe、旧 REST API、下载/导出、页面按钮与 AI Action。记录方法/路径、调用的业务服务、身份来源、当前页面/Action/数据范围检查位置、候选与运行版本；不能只从 Manifest 或新路由推断旧路由已受保护。配置仅记录开关及是否配置，不能记录秘密。

- SaaS 员工通道使用可信 SaaS 身份及当前资源授权，不以本地账号、角色或白名单再否决已授能力；鉴权失败或 SaaS 不可达不得回退为旧凭据放行。明确保留的旧账号/角色/登录入口和独立 C 端用户按各自原有规则使用，单列身份来源与边界，不因本规范删除或关闭。多方身份、同步与历史保留见[员工授权与多方身份](employee-authority.md)。
- 不一刀切禁止 Basic 等技术：它可作额外外围保护，但不能替代业务鉴权。独立运维、健康检查、签名事件和机器任务分别记录用途与信任边界；使用 SaaS 的遵循真实平台契约，企业服务委托可按 [企业服务器内业务服务对接](intra-enterprise-service-integration.md) 由获权开发 AI 实现。运维凭据不能冒充员工，机器身份不能静默取得任意员工的业务权限。
- 不只检查 `AUTH_ENABLED` 之类的名字。沿每条可达路由追到鉴权分支和数据访问；禁用开关不等于旧路由不可达，未认证返回 401 也不能证明有效旧凭据不会绕过 SaaS。
- 旧入口按实际调用方与本次授权选择关联同步、保留原认证或明确迁移；不得仅因与 SaaS 并存就删除接口、关闭服务、重置密码或改业务角色。区分获准保留的独立通道和伪造 SaaS 身份的绕过，记录各自验证，技术预检不能代替真实员工验收。

浏览器业务 API 使用实时 `session-check`；平台机器 Action 按现行契约由 SaaS 在授权后签发短期 JWT，子系统复验签名、期限、主体、资源、范围及业务条件。两条链分别验收；仅测试 Action 签名/过期不能证明 SaaS 撤权全链已通过，也不能擅自给旧协议增加未支持的字段或在线校验要求。无业务数据的 HTML/静态壳可加载，不代表其业务读取/写入获权。

企业服务专用入口单列机器主体、委托范围、可信来源员工及结果查询权限，不把该机器身份塞入员工 `sub` 或复用员工 Cookie。来源员工入口继续实时核权；目标按明确业务委托鉴权，代理员工模式另核当前目标权限。使用独立机器入口不是给员工开放绕过 SaaS 的裸 REST 路由，须实测错误主体、企业、操作、文件、撤销和恢复。

## 三种人员含义不能混用

| 含义 | 权威来源与写入要求 |
| --- | --- |
| 当前操作者、创建人、审批人 | 从已验证会话/Action 的稳定 `sub` 写入，不能由请求体中的 `createdBy`、姓名或选人结果替换；页面与 AI 走同一服务 |
| 被分配的企业员工，如负责人、班委 | 从受控员工目录选择稳定 ID，保存时按当前操作权限精确 resolve；操作者仍单独记录，选了他人不等于代他登录或提交本人操作 |
| 外部联系人或历史署名 | 可以作为业务文本/快照保存，但明确其非 SaaS 员工身份，不用于登录、授权、认领或个人统计；不强迫外部联系人注册 SaaS |

涉及员工选择和历史迁移时继续执行 [员工目录与历史身份核查](employee-identity.md)，不能以隐藏 ID 输入框代替后端核验。缺少平台能力时记录具体依赖并保留已有合法入口；不临时另造一套员工授权、按姓名猜测或让负责人手抄 UUID。业务资料可按可信稳定身份自动补齐。

业务参与、任期、分组和审批资格归子系统，真实业务资格仍可限制某项操作；须与 SaaS 的登录/页面/Action 权限分别判断、分别报错。不能把“缺本地姓名/显示名/登记副本”伪装成资格要求。新建名单时说明是否需要报名或分组，不把 SaaS 注册自动解释为参加所有业务，也不要求每名员工重复注册另一套登录账号。

个人记录与个人榜单按可信稳定 ID 关联和聚合。姓名改变不能生成另一个人；明确的按期/按组业务统计可保留其维度，但显示姓名不能成为拆分身份的键。历史姓名/分组快照的保存与当前账号归属分开处理。

## 必须执行的场景

使用隔离测试账号与可恢复数据，执行目标版本的真实路由、服务和数据库断言；不能仅 monkeypatch 掉鉴权后证明它通过。每个适用场景同时核对响应、实际数据归属及失败时无业务副作用。

| 场景 | 必须验证 |
| --- | --- |
| 两个获权员工与正向流程 | 分别完成获权操作、回读自己的稳定 ID；不能靠拒绝所有请求让安全测试变绿 |
| 旧账号与非员工入口 | 获准保留的旧入口按原角色正常使用；独立 C 端白名单有效但不取得员工目录/权限；伪造身份头或旧凭据不能冒充 SaaS 员工通道 |
| 撤权、停用、过期与鉴权服务故障 | 已有 Cookie 或有效旧凭据不能恢复访问；页面、直接 API、AI Action 均遵守各自契约，失败时不读出数据或写入 |
| 客户端伪造身份 | 伪造 `userId`、`createdBy`、姓名、企业或范围，不能换操作者、归属或授权；获权负责人选择与操作者字段分别断言 |
| 姓名和名单边界 | 同名、改名、无显示名、无本地名单分别验证；合法无名员工仍能完成允许的本人流程，真实业务资格不足仍被明确拒绝 |
| 受控选人 | 未授权搜索、跨企业/范围、搜索后目标停用、目录故障均拒绝；不能回退手填，保存再次核验，见员工目录参考 |
| 业务浏览器流程 | 对本次影响的表单实际填写、点击、提交、回读，覆盖电脑与手机；后端测试不能代替 disabled/required 等前端门槛检查 |
| 历史修复（仅适用任务） | 受影响来源全量分类、所有引用、冲突、事务异常、重复执行及分数/快照守恒，按员工目录参考执行 |

模板测试只证明模板；扩展后的业务系统必须用自己的入口、表单和存储重跑。合成鉴权模拟、源码/Schema 检查、预登记拒绝探针、隔离浏览器、真实员工操作分别报告；不替真实员工打卡、审批，不自动调整真实角色。`e2e_acceptance.py` 的技术通过不等于本表通过。

本表不缩减平台契约既有的全端验收要求；共享登录/鉴权的变更会影响多个页面，不能把“本次表单”解释为只验用户报错的一个按钮。

## 收尾与后续修复

沿用项目交接文件记录：适用入口/人员关系、源码与运行版本、测试命令及证据引用、通过/失败/未测/不适用及理由。状态和证据不能只填一句“已遵循 Skill”；检查表本身不是执行证据。凭据与个人明细只放受控资料，不放公共 Skill 或 Git。

遗留项写入项目任务及交接，注明影响、责任层、验收条件与下一步，不能修复某个按钮后把历史身份问题一并标完成。按同一来源核查相关入口和引用，但不借机迁移无关业务数据。无法证实的历史归属保持待确认，不以负责人授权修复代替身份事实。

SaaS 提供公共身份、目录、权限与失效机制；子系统落实每条业务路径及业务关系；Skill 维护契约、模板和验收。分别记录修改、合并、稳定包发布、各运行服务部署与验证。先发布 Skill 不会自动停用或升级旧系统；后续逐系统评估、修复和验收，不要求正确实现的系统为了凑齐发布次数重部署。
