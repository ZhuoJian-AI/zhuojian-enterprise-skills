# 子系统可用性与维护提示

每个 `applicationSlug` 是独立发布和故障边界。SaaS 全局维护只用于平台自身；某个子系统不可用时，其他子系统、工作空间和助手不能被一并冻结。`contractRevision` 保持既有 `2.4/2.5`，不新增 Manifest 中的实时状态字段。

## 状态证据

| 状态 | 唯一可信依据 | 员工提示 |
|---|---|---|
| 正常 | 已登记入口的 `GET /health` 返回 2xx 且业务页面完成可信 `ready/context` | 不显示状态条 |
| 计划维护 | 当前运行服务的 `/health` 返回 HTTP 503、JSON `{"code":"SUBSYSTEM_MAINTENANCE"}`，并带有正整数 `Retry-After` | “当前业务系统正在维护”，仅针对该系统 |
| 突发不可用 | `/health` 超时、连接失败、非 2xx 且无上述准确维护标记 | “当前业务系统暂不可用”，不得称“升级中” |
| 页面连接未就绪 | 健康检查正常，但 iframe 未收到该次启动的可信 `ready/context` | “业务页面尚未建立连接”，提示重试或检查嵌入配置 |

`/health` 是无副作用、无需员工 Cookie 的固定端点，不返回内部路径、异常栈、凭证或部署细节。普通健康响应沿用 `{"status":"ok"}`。计划维护响应应使用 `application/json`、HTTP 503 与 `Retry-After`，且只在目标服务实际进入受控维护时给出；构建候选、等待登记、已登记但旧版仍健康，均不得发维护信号。单纯 HTTP 503、iframe `load` 事件、平台 API 错误或一次网络失败，不构成“正在升级”的证明。

## 服务端与页面行为

- 计划维护先停止接收新的业务写入，再返回结构化 503；读写使用同一维护状态，不得一边宣布维护一边接受 Action、上传、审批、导出提交。正在执行的写入先安全排空或保留幂等回执；不把未知结果自动当失败，也不自动重发。
- 子系统后端对页面请求和 AI Action 使用同一写入门禁；SaaS 的提示不能替代子系统真实拒绝。业务错误、权限拒绝、会话过期和未保存草稿分别处理，不冒充维护。
- 嵌入 SaaS 时由当前应用容器呈现状态，不在 iframe 内叠加第二条相同提示。独立打开时子系统在自身页面显示可关闭状态条：维护或故障期间可手动检测恢复，恢复提示应自动消失且有关闭按钮。
- 既有 iframe 一旦就绪，不因健康探测失败而卸载、刷新或遮断输入；保留当前模块、滚动、表单、附件选择和助手上下文。对未就绪入口可在健康恢复后由用户手动重连并申请新的一次性 SSO 票据，不复用旧票据。
- 恢复后只重新查询当前页面必要数据，不自动提交草稿、文件、Action 或 AI 工具；手机与桌面均要可读、可点、可关闭，不使用浏览器阻塞式 `alert/confirm` 汇报状态。

## 发布与验收

Runtime 测试和镜像构建期间维持旧健康版。当前宿主发布入口只有一个数据挂载和服务端口，既有应用可能在启动时同步数据或运行后台任务；因此更新采用受控维护完成一致备份及单实例切换，不宣称零停机，也不未经证明双起。AI 在已确认的具体业务发布范围内自行执行，无须再让负责人逐项批准或操作前端。

实际停机前先持久记录恢复事务，Nginx 对该应用的页面、SSO、Action、上传和 `/health` 统一返回维护响应，再停止原实例，备份并验证后启动候选。候选健康后才重开；失败先恢复原实例并核健康，再开放原入口。备份期间进程中断也保留恢复标记，下次本应用命令继续恢复。这个维护窗口用于必要的数据一致性，故障不得伪装成计划维护；维护时长取决于数据量和启动时间。将来要改成并行候选，需要先落实隔离数据、迁移兼容及后台任务单活，并以实际业务验证证明可安全切换。

每个应用独立发布和回退，健康检查不代替 SSO、页面、Action 与真实员工验收。代码回退不会自动撤销数据库迁移或外部同步结果，业务实现必须保留兼容或提供明确的数据恢复步骤。

至少验证：健康 200；计划维护的 503/标记/`Retry-After` 与写入拒绝；无标记 503、断连和超时显示故障而非升级；健康但 Bridge 未就绪；恢复后当前草稿仍在且没有重复写入；关闭或自动收起恢复提示；移动端与桌面、嵌入与独立入口。测试不得通过真的破坏线上服务或真实员工业务数据来制造故障。只完成 Skill 更新不等于三个业务系统已经适配部署。
