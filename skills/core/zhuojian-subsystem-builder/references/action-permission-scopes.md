# 操作权限与记录归属

企业管理员只勾选能理解的业务能力，不配置“本人／部门／全企业”“沿用角色范围”等技术范围。Action 的 `name`、`description` 必须讲清能做什么、处理什么对象；SaaS 负责勾选、保存与有效权限，子系统负责真实业务规则和记录过滤，Skill 负责模板和发布校验。不能只隐藏范围控件而继续继承错误默认值，也不能统一改成全企业。

例如“查看本企业全部商品”“修改自己负责的商品”“审批本部门请假”。“自己负责”必须有真实分配字段及服务端归属规则，不能拿创建人代替；当前只支持创建人过滤的系统应准确写“修改自己创建的商品”。页面打开权限不是查看全部数据的权限，页面、Action、记录归属仍分别校验。

## 新增操作必填、旧契约兼容

保持 `contractRevision` 2.4/2.5，不新增权限模式。新建、新增及本次改变权限边界的 Action 必须声明并实际实现以下一种固定含义；已有缺失或多范围操作按下文精确基线兼容，不能根据 CRUD 名称推断或补成 all：

| 业务含义 | permissionPolicy | 执行要求 |
|---|---|---|
| 企业内公共内容读取 | `{"group":"public_read","mode":"public_read"}` | 仅 query；仍要求登录、同企业、页面与 Action 授权，只返回已发布公共字段 |
| 员工本人记录 | `{"group":"personal","mode":"self"}` | 服务端可信用户 ID 限定本人；管理角色也不能扩大该 Action |
| 明确的业务管理能力 | `{"group":"management","mode":"configurable","supportedScopes":["all"]}` | `supportedScopes` 只含一个已实现的范围；管理员勾选即写入该操作的固定授权，不继承角色默认值 |

支持范围枚举仍为 `self/department/department_and_children/custom_departments/all`，仅供开发与服务端执行，不出现在企业管理员的通用范围选择器中。新能力的 management 只选一项；同一业务确需不同边界时拆分稳定 Action，分别明确名称并调用同一业务服务。固定模式不填写 supportedScopes。公开模式不得用于新增、修改、审批、删除或导出。`all` 仍限当前企业，不是跨租户访问。声明不授予页面或 Action 权限。

新增带策略的 Action 不自动向既有普通业务角色扩权；系统研发者仍由平台托管授权，但固定个人归属、停用、契约移除、确认和业务状态检查同样有效。

## 旧系统迁移与发布门禁

1. 从当前已部署版本只读保留原 Manifest，记录源码／运行版本、Action 键、策略及既有角色有效授权；不能把候选自己当旧基线。
2. 新增或改变边界的 Action 必须固定含义。已有多范围操作可以暂时保留原后端语义；通过可选展示元数据 `permissionPolicy.scopeLabels` 为每个支持范围提供完整的业务能力名（trim后非空、最多160字，键集合恰好等于supportedScopes），例如 `{"self":"查看自己创建的商品","all":"查看本企业全部商品"}`。重复名称仅在已核实业务效果完全相同时允许，SaaS可折叠为一个能力勾选；保留旧授权scope，新授按已核实同义组选择最小可用边界，不按标签推断权限。它仅用于management展示，不参与执行、不授予或改变权限。SaaS须在电脑和手机呈现这些明确业务勾选项，保存只改变该Action授权，不显示技术下拉、不借用其他角色范围。旧操作缺少完整scopeLabels时，管理员只能保留或取消已有授权，不能选择新范围；交接输出待升级，不能按CRUD加通用标签猜测业务。指定部门／目录目标沿用已核对配置，不因缺少目标而默认全企业。
3. 使用 `audit_permission_upgrade.py --current <候选> --baseline <已部署Manifest>` 核对差异。既有未变 `moduleKey/actionKey/operation` 及策略 `group/mode/supportedScopes` 可以输出 `legacyUpgradeRequired`；改名、补业务说明和scopeLabels不改变授权边界，移动模块、新增键、改变operation或策略语义不能借基线豁免。
4. 源码、端点及登记脚本均强制检查勾选契约。完全固定的候选无需基线；有已核旧操作时，分别传 `--permission-baseline <已部署Manifest>`，明确输出待升级清单。无基线的缺策略或多范围操作、无业务名称／说明和错误策略必须失败。基线仅用于兼容，不修改角色、业务数据或运行时协议。
5. 逐项对照迁移前后授权。查看企业公共商品和修改／删除是不同决策；若业务明确变更“仅创建人查看”为“查看全部商品”，单独迁移查询授权，禁止顺带扩大写入、导出或通知权限。管理员停用、撤权、企业隔离、固定个人操作和确认继续优先。

`scaffold_subsystem.py --record-access personal-created|enterprise-shared` 要求开发 AI 按已确认业务显式选择骨架，生成单一范围及准确名称；它不是向管理员新增技术配置，也不能代替真实业务模型。混合业务按 Action 重新设计和测试，不把模板统一范围生搬到生产系统。

## 统一执行

- 统一身份检查覆盖可达的旧 REST API、独立入口、文件与 AI Action，不只覆盖 Manifest 中的新接口；本地密码、旧会话等不能成为鉴权失败后的放行路径。入口盘点、合法运维边界和实际行为验收按 [统一身份验收](identity-acceptance.md) 执行。
- SaaS 将角色中的可选 `page_access.action_scopes` 解析为当前 Action 的有效范围；子系统使用实时 session-check 的同名 `actionDataScopes` 或 Action JWT 的有效范围，不解析浏览器自行提交的授权配置。
- 多角色只合并真正授予该 Action 的范围；不能借用另一个无关管理角色的 all。AI 与页面调用同一服务函数，AI 开关不扩大范围。
- 页面初始化分别读取获权公共内容与个人内容。没有管理查询权限时隐藏管理区或报告局部拒绝，不把公共页面整体拒绝；没有公共 Action 授权仍拒绝对应读取。
- 以可信用户 ID 校验创建、读取、修改和撤回的归属；不能按客户端 userId、姓名或任选记录 ID 认领他人身份。管理能力不自动允许冒充他人提交本人操作。
- 显示姓名是可选展示元数据，不是授权凭据。SSO `displayName` 或实时校验 `display_name` 缺失时，只要可信用户 ID、页面、Action、范围及业务条件有效，本人操作仍应可用；不能以姓名为空禁用提交，或把只读姓名输入设为必填。可回退到服务端已核实的同 ID 名单姓名，不能按同名认领历史记录。
- 纠正已核实错绑须先核对 SaaS 稳定 ID、目标成员和全部关联记录，备份并在有前置条件的事务内修复；遇到他人的业务记录、目标冲突或核查后数据变化就停止。纠正绑定不等于授权补打卡、改分或转移未核实的历史记录。
- 历史记录没有可信归属时，列出不含敏感内容的待确认记录引用；受限读取隐藏它们，写入拒绝。禁止按姓名猜测回填或归给当前登录者，不因此阻断公共已发布内容。
- 员工选择、业务名单和历史修复按 [员工目录与历史身份核查](employee-identity.md) 执行：选择后须服务端精确核验，历史修复核对全部引用、分数与快照，不只检查名单主表。
- 需要把旧聚合查询拆为公共/个人/管理 Action 时，保留旧查询的安全兼容行为，不将旧授权悄悄改为公开全部数据。resultSchema 与实际投影逐项一致。

## 聚焦验收

管理员电脑和手机均只需勾选、保存和重新打开：无通用技术范围控件、无“沿用角色范围／本人记录”标签；勾选后实际保存对应 Action 范围。使用非研发普通测试员工验证获权读取有数据、取消勾选拒绝、同角色不同员工归属正确；空结果与无权限分别提示。旧多范围逐个勾选、取消、保存回读，不改变无关 Action 或既有写权限。Schema／静态门禁不能代替这些真实验收。

两个独立测试员工分别读取公共内容和自己的记录；交换记录 ID、伪造用户 ID/姓名、直接 API 和 AI 调用均不能读取受限记录或操作他人数据。单独测试获权管理范围及范围外拒绝、固定本人不可扩大、多角色不串权、撤权生效、历史归属缺失不阻断公共页面。测试使用可恢复数据，不自动调整真实员工角色，也不以 Schema 校验通过代替运行时隔离证据。

前端和服务端分别覆盖：可信身份有姓名、无姓名、没有本地名单、同名或错绑名单、无 Action/范围、撤权和真实业务条件不满足。电脑与手机均验证只读姓名为空时获权本人表单可以提交，浏览器伪造姓名不能改变归属，管理查询失败不阻断获权公共/本人流程。隔离模拟提交与真实员工提交分别报告，不为验收替真实员工打卡。
