# 员工授权与多方身份

这是身份与授权的结果约定。AI 根据现有系统、可信证据及本次授权选择实现、同步和验收方法，不增加固定业务流程、另一个决策器或重复审批。

## 管理员授权应当生效

企业员工通过 SaaS 入口使用业务时，当前 SaaS 角色决定可见页面、可执行操作及对应数据范围。后端校验签名、资源、企业和实时授权是在执行同一权威；“没进本地 users、未绑原账号、没有本地管理员标记或项目岗位”不能再成为额外的员工放行名单。

企业管理员、系统研发者在本企业实际获授的业务能力应能使用；本人操作仍记录本人，跨企业隔离、真实业务状态、版本、幂等和历史归属保持。页面可见不等于所有写入已授权。工作空间、个人范围和逐 Action 策略由 SaaS 解释，子系统不按角色名称重算或互相借权，也不能借业务岗位把已授操作再要求管理员开一次。

## 三处身份可以同时存在

钉钉/原企业软件、SaaS、子系统可以各有员工 ID；它们应能通过经过核实的来源主体与稳定 ID 对应同一员工。先复用现有可信绑定、目录或同步服务；业务确需资料时可在获权访问时幂等补齐，不把第一次登录生成空档案称为原企业人员全量同步。

员工主档的姓名、部门、在离职等字段各有明确来源，角色授权由 SaaS 主责。已有同步支持事件或按需校对时沿用其机制，不为本 Skill 新增后台轮询。变化、失败和冲突留下真实状态，可重试且不重复开户；断网或缓存身份不能当作当前 SaaS 授权。未接通原企业目录的部分明确记待接通，不假称三方同步完成。

原账号、旧角色、密码入口以及业务记录保留各自合法边界；不因为接入 SaaS 删除旧角色、关闭原入口或让老员工失去原能力。SaaS 通道不回退成旧密码登录，也不将多个通道的权限无边界合并。只读源通过明确服务委托消费获权能力，记录真实 SaaS 操作者，不冒用某个原员工账号；原源账号/角色与业务数据保持。

关联键包含企业和身份来源，不能按同名、显示名或未经核验的邮箱认领。已有绑定冲突时保留双方与历史数据，核实后按已授权的身份修复范围处理；不让新员工先手工处理技术绑定才能进入自己的获权业务。原记录 owner、创建人、审批人、金额、积分和历史快照不随资料同步重写。

## 独立用户与白名单

C 端客户、学员、合作方或附属用户保留独立账号、本地角色或白名单；接入应用用户能力后，原系统登记的可登录账号关联到 SaaS 平台身份和本应用使用关系，不要求登记成企业员工，也不因此获得企业目录或 SaaS 员工能力。平台有此人，不等于此人能进其他系统。同一个人同时具有员工和客户身份时保留来源与使用上下文，只有可信证明或原有精确绑定才关联；协议、可用客户端与兼容方式见[应用用户与平台身份](application-users.md)。未接入的旧通道保留并如实标注，不以修改Skill冒称已经同步。

员工的实际业务参与或任期属于业务数据；它不能包装成第二道员工登录/授权名单。C 端白名单也不能借名套用于已经由 SaaS 获授能力的员工。

## 能证明什么

有代表性的证据包括：SaaS 企业端授角色后，无本地配置的新员工实际打开并完成对应业务；管理/研发及普通角色按各自授权工作；撤权/跨企业请求拒绝；旧账号仍可按原边界使用，数据数量与归属保持；同名不合并、并发同步不重复开户、关联失败可恢复；独立 C 端用户仍能按原规则使用。

以本次变化选择需要的真实入口与电脑/手机验证。源码测试、真实平台授权、部署版本、历史数据对账、原企业目录同步、客户端 Skill 更新分别报告；Skill 文档发布本身不能证明其中任何运行时已修复。
