# 多系统对接与整条业务流程验收

用于三个、四个或本企业全部明确应用/模块共同完成业务。先读 [跨系统对接与受控配置](cross-system-integration.md)，沿用其中的选型、真实身份、单计划CLI与业务处理要求。本页补充整体拆分和验收；两个应用的简单对接继续按原流程。

## 确定整体业务范围

开发 AI 先从当前获权目录、真实代码和运行版本建立关系图，再用业务语言向负责人说明整体结果。每个业务对象指定唯一权威服务，其他系统只按已确认需要查询、提交或保留结果引用；一个对象无需因系统数量增加而复制业务记录。

“全部系统”要展开为本企业、同环境、当前可见且获权的具体应用/模块清单，核对停用项、未知归属和目录遗漏。对尚无权限发现的系统标明缺口；全企业清单没有核全时不得声称全部覆盖。只加入实现该业务目标所需关系，不能生成所有应用互相读写的通配授权。后续新登记应用不自动纳入。

向负责人确认的整体说明至少包含：

- 参与系统与模块、各自职责、业务起点、必需分支/汇合和最终完成条件。
- 传递的资料/字段/文件及对象映射、权威存储、允许的查询和写入、操作者及可见范围。
- 失败或部分完成时的处理、已有业务影响、拟发布范围、测试资料和清理方式。
- 需配置的精确关系及配置期限；解释为允许哪些系统配合，不让负责人选择事件名、处理机器确认或逐个操作前端。

负责人在 Codex 明确确认这份整体范围一次即可；已确认且包含本轮全部精确关系的说明可复用。用稳定业务任务标识和方案修订号保存脱敏确认引用、参与清单及关系映射，记录在项目 `docs/integration-workflows/<workflow-id>.md`，并从各相关项目 `docs/ai-delivery.json` 的既有证据字段关联。交付文件不是平台授权令牌、Manifest扩展或运行调度定义。

同一确认可支持范围内多个精确计划的技术执行，但各计划仍须通过真实后端和各自 Runtime 的授权检查。新增系统/模块/关系方向、扩大数据/操作/可见范围、改变权威归属、增加业务副作用或扩大配置期限时，先说明差异并取得对应确认；保持完全包含在原范围内的拆分或顺序调整无需重复追问。契约/摘要漂移按单计划规则重新核对，不自动沿用旧机器确认。整体确认不代替员工运行时业务授权、危险操作确认或独立后台任务委托。

## Codex 自行拆分与实现

对关系图中的每一步分别选择页面复用、同应用业务服务、获权 API/Action 或异步事件；不是每一步都要创建事件计划。真实业务处理、文件访问、身份传递、幂等、结果查询及权限校验先落入对应子系统。仅登记路由不能生成跨系统业务编排；需要持续运行的分支、队列和重试必须由真实业务服务实现，不能依靠本地交付文档或已结束的 Codex 会话运行。

对于确实需要的平台事件关系：

1. 先用`discover`分页读当前Runtime参与计划至has_more=false，按应用对用`routes`读既有精确关系，再核完整端点、模块、事件版本、权威归属及当前有效状态。已匹配关系以只读证据复用，标明既有计划及所有者；没有读取权限的范围列待核实，旧最近100项列表不是完整清单。接管合法手工旧路由按单计划页显式adopt_route_id，纳入已确认整体范围；其余关系不能覆盖或盲目重建，平台冲突不能靠换请求ID绕过。
2. 现有单计划最多两个应用、八条精确边，且应用/模块图连通。先按应用对分组，再按模块连通块和八边上限拆为合法计划；同应用跨模块也按实际约束处理。每条必需业务关系恰好映射到一个新计划、一个已核实既有配置或一个非事件实现。多个计划的集合不受单计划两应用限制，仍须完全落在已确认范围内。
3. 为每份计划保存稳定 `request_id`、原申请 Runtime、参与 Runtime、精确关系、依赖和关联的整体修订；平台返回后保存真实 planId、公开授权摘要、version、绝对 apply_expires_at 和状态。整体索引及依赖字段只保存在本地交接中，不能作为新参数发送给现有API；业务关联ID只有真实已实现载荷/服务支持时才能传递。
4. 发布/订阅和目标处理须先实现并同步，再提出 `runtime_endpoints` 计划。用已有 `integration_plan.py` 对每份计划完成能力发现、提案/读回、各端本机确认、原申请端 apply 和状态读回。单Runtime拥有两端时每计划确认一次；多Runtime由AI各用本机凭证完成，负责人不重复运行命令。检查每份计划自己的共同deadline，不能把整体确认日期当作无限期机器授权。

整体索引至少让后续 AI 能逐项找回：关系到实现/计划的映射、稳定请求与申请端、当前配置/确认状态、期限、阻点及真实证据引用；不含密钥、原始资料或失败响应正文。方案修订后保留旧索引和已完成结果，不用新文件名隐藏失败或重新提交未知请求。

## 依赖、部分成功与撤销

先准备目标服务、查询/结果能力及必要的下游关系，再开放上游业务提交。根据真实依赖安排逐项配置和测试；独立分支可并行。需要多个分支全部完成才能继续时，业务服务必须核对各自真实结果后汇合。环路要有明确触发边界、稳定业务操作标识和防重复/防回环控制，不能把数组顺序或配置顺序当作运行时执行顺序。

平台目前按独立计划应用，不提供跨计划原子提交、整体回滚或批量授权事务。维护“未执行／已配置待业务验收／失败／结果未知／业务已验”的逐项状态：

- 一项失败时停止依赖它的后续动作，保留其他已成功状态；不把整组显示为完成。若支持分阶段启用，保持上游提交受控直到必需依赖已就绪；已有正常业务的关系和服务继续按原约束运行。
- 写请求结果未知先按原CLI身份只读查询：提案/request_id、apply与verify由原申请端读回；参与端confirm/reject/revoke由该参与Runtime按planId核对自己的有效确认或决定，不能借申请端的current_runtime状态冒充另一端。仍不确定就保留unknown，依赖步骤暂停。相同业务操作重试先回读目标结果，已完成部分不重复写入。
- 恢复时逐项检查目录、归属、契约、有效授权与期限，只推进仍获权且未完成的部分。过期、拒绝或撤销项遵循单计划流程，不自动换ID扩权或继续重发。
- 遗漏投递先按原plan/edge分页`recovery-list`，用目标读回区分已完成、失败及未知。在原授权事件窗口内按稳定请求分批`recover`；新计划不补跑旧历史，在途/未知先对账。整体索引记录恢复request_id、精确项与回执，下一Codex只读同ID接续，不把排队或整批受理当整链完成。新增不相关订阅应由revision2精确契约保持旧链，验收须实测；已漂移无兼容证明的旧计划不能假定自动恢复。
- 负责人要求停止或撤销时，先按真实支持能力控制新的业务提交，区分本次新建与原有共享关系、记录其他使用方和受影响范围。仅在获权且确认影响范围内逐计划调用revoke并读回：当前实现停用该计划保存的路由，将关联待投递/失败项标失败并停止普通重试；审计保留。它不回滚其他计划、删除已完成业务记录或保证撤回正在进行的写入。删除数据、补偿操作或影响原有使用方须在已确认范围内，否则先确认差异；旧计划已撤销、路由不活跃后重新建立关系，也须走新的有效计划，不复活旧授权。

## 整条业务流程验收

以负责人确认的完成条件验收，覆盖全部必需关系、分支、汇合和最终可见结果。使用获授权账号及测试资料，从真实业务入口发起，记录所有参与应用的部署版本及同一次业务操作关联证据：

| 场景 | 必须取得的业务证据 |
| --- | --- |
| 三系统顺序流 A→B→C | A提交、B真实处理结果、C真实记录/操作结果和来源最终读回；稳定业务对象映射、各方记录ID/版本及结果可对账，原件传递核对摘要，解析/转换产物按已确认规则验证 |
| 四系统分支汇合 A→B、A→C、B/C→D | 两分支均真实处理，D只在约定前提满足后完成；不能以先到一支或单条回执报整链成功 |
| 当前全部明确系统 | 对照确认清单逐项覆盖所有必需参与者和关系；可只读参与，无关系统无需构造写入，缺任一必需项保持未完成 |
| 重复、冲突与跨步骤恢复 | 重放同一逻辑操作不重复新增/触发；相同ID不同内容拒绝；中途失败/超时后回读并仅恢复未完成部分 |
| 权限、撤销与传播 | 每步核对可信操作者或明确机器委托及允许字段/文件；错误企业/环境/模块、无权员工与撤销场景不能借中间系统获取更大范围 |
| 失败、未知和缺分支 | 校验失败、仅收件、不可确定或缺必需分支时，来源及最终结果保持真实未完成/失败状态，恢复符合业务约定 |

事件步骤保存真实deliveryId、目标processed结果及业务记录引用；非事件步骤保存其实际调用与获权回读证据，不伪造deliveryId。每份 `integration_plan.py verify` 只复核已保存目标回执；多个verify通过仍须补上相邻业务步骤、跨计划结果关联、所有必需分支和最终页面/业务回读。逐项配置成功也不能标记整链业务成功。

新增或修改页面分别验收电脑和手机；既有授权后端配置不强制打开管理员页面，没有访问的页面不记为已验。浏览器模拟、真机、未测项分别说明。各项目 `docs/ai-delivery.json` 按原Schema记录自身真实绑定、结果和跨层缺口，整体索引关联各方证据，只有全部必需完成条件满足才标整链已验。

交付时用业务语言说明整体做成的结果、各系统职责、可使用角色及恢复/撤销入口；逐项列明配置已应用、业务已验、未知/受阻。分别报告 SaaS／Skill／子系统修改和发布状态。当前平台无能力或某端无获权连接时，继续独立可推进工作并产出确切缺口、责任层及下一步，不要求负责人逐个操作前端或转述“找平台开通”。
