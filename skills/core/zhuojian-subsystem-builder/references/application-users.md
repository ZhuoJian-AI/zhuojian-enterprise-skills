# 应用用户与平台身份

按现有系统的事实选择适配方法。本页是可组合的接口与边界，不规定AI的工具顺序、固定开发流程或统一登录页面；普通员工系统无需为了接入这一可选能力重建账号库。

## 三种含义

| 对象 | 平台表达 | 原系统保留 |
| --- | --- | --- |
| 企业员工 | 现有企业User、角色与员工SSO；访问记录可关联平台主体 | 原ID、业务资料与历史记录；SaaS入口不另设本地放行名单 |
| 客户/学员/合作方等可登录用户 | 无须企业成员关系的平台主体、可信来源账号、本应用使用关系 | 原账号认证、密码来源、业务角色、客户/合作关系、登录页面 |
| 业务文本中的联系人或历史署名 | 不因一条联系人数据自动开户 | 原业务文本或快照 |

SaaS有此人不等于所有企业和所有系统都有此人。子系统的获权用户管理者可管理本应用用户；不能据此创建企业管理员、读取其他企业目录或修改其他系统。平台企业端的“成员与用户/系统用户”按企业和应用聚合登记，企业成员与技术身份保持原入口。

## 发现与信任

从现有平台能力接口读取 `features.applicationUsers.supported` 和其实际endpoint。平台尚不支持时保留原合法入口，记录依赖；Skill升级不代表接口已经上线。新能力与2.4/2.5员工SSO、Manifest及Action兼容，不要求提升契约版本。

服务端复用本应用现有 `zjss_` 交换凭据，通过HTTPS调用 `/api/v1/subsystem-users/*`；凭据不进浏览器、公开包或日志。认证绑定应用，不能从请求体指定另一应用。现有企业初始化和SSH授权保持；不要为了登记用户新增一个Root口令、复制用户密码或重做Runtime。

可按现有语言/网络库实现；[标准库Python客户端](../assets/application_user_client.py)是可独立取用的例子，不要求改框架或数据库。

## 来源登记与版本

`POST register`接收：

```json
{"external_id":"原系统稳定账号ID","display_name":"称呼","business_roles":["原业务角色"],"relation":"customer","source_label":"原系统账号","source_version":1,"is_active":true}
```

`relation`可为`customer`或`collaborator`，本企业员工关系由可信关联推导。稳定键为平台确定的应用来源加`external_id`；姓名、手机号和邮箱不作为自动认领依据。新账号登记不创建企业User，不授企业管理能力。

`source_version`是每个来源账号的持久递增版本：同版本同快照重试幂等，同版本不同快照409，旧版本不覆盖新状态。来源更新可停用自己的账号，不能清除平台管理员的应用停用。复用已有事务/事件/补偿机制；无现成机制时按规模选择可靠落盘和重试方案，不要求额外服务或固定轮询。既有账号按已核实归属补登记；所属应用不明就保留待核实，不猜归属、不删除账号。处理已删除/停用来源的状态，避免只同步新增。

平台返回`subject_id`、成员关系`id`、`application_id`、`version`和实际状态。保留原账号/角色、密码、学习或订单数据、owner及历史署名；平台ID作为附加关联，不批量重写业务外键。原角色可以继续用于原通道；员工SSO的已授权能力不受旧白名单再次否决。

## 原账号登录和会话

子系统先按其真实认证方式验证本人，再由服务端`POST login {external_id}`交换应用会话；不能让匿名浏览器提交某个外部ID就替他登录。登录页、验证码或其他认证外观由子系统负责。平台仅颁发本应用`application_user`会话，不是员工会话，不能调用企业管理、员工目录或其他应用接口。

业务请求以`POST session-check {session_token}`复验当前应用状态。成功返回可选`renewed_session_token`时保存更新；拒绝/撤销不能通过自动再次调用login绕过。过期让用户在原入口重新认证，服务故障保留原业务数据和同步待办并清楚呈现，不能把缓存成功当当前授权。`POST logout`撤销该来源账号已发会话；本地会话同步失效。来源凭据和用户会话各自限定范围。

与尚未迁移的独立历史通道并存时，明确哪条已接入平台访问管理；不得把未接入通道冒称已能平台撤权，也不能因新通道故障关闭无关合法入口。员工SSO仍用其原session-check和权限，不加应用账号前置。

## 已有身份、邀请与原绑定

员工SSO换码的可选`claims.platformSubjectId`/`identityLinkToken`可用于原账号登记时的`identity_link_token`。已有员工也可使用本人认证调用`POST /api/v1/users/application-identity-proof {application_id}`；另一应用的已认证独立用户可通过其来源`POST identity-proof {session_token,application_id}`取得目标应用限定的五分钟证明。证明只关联同一人，不授目标企业员工身份或目标应用访问权。原账号的本人认证、平台证明与目标应用登记分别有效。

当前企业管理员可通过`POST /api/v1/applications/{app}/users/{member}/employee-binding {employee_user_id,expected_version}`迁入已经核实的“原账号→本企业User UUID”绑定。仅用于可信精确映射，保留审计与历史主体；不能按姓名/邮箱猜测、用一个默认员工认领所有账号，也不能合并其他应用的身份。

平台管理端或本应用获委托管理者可创建本应用邀请。一次性令牌通过原系统入口`zj_invitation`交给本人；服务端`POST invitations/resolve {invitation_token}`取得该邀请的目标及业务提示，可信原账号在登记时传`invitation_token`消费。邀请不保存密码、不自动发消息、不替代原系统本人认证；新用户开户沿用原系统现有能力。已有账号的角色不能被邀请偷偷提升；原系统决定新账号业务配置并回报真实结果。暂未接邀请的旧系统不能声称邀请已可用。

## 结果与交接

按受影响范围选择能证明结论的测试：无企业成员的新用户、原账号/角色/数据保持、同名不合并、精确旧绑定、其他企业人员不变成本企业员工、来源版本/断网/重启补偿、平台暂停及恢复、旧员工实时授权、越权/跨应用拒绝。数据库迁移和发布分别有回滚兼容证据，电脑与手机、真实平台与合成测试分别记录。

项目交接保存实际应用ID、来源、员工/独立入口、绑定证据来源、能力版本和部署/验收状态；秘密留受保护配置。负责人只需提出业务目标，技术调查、实现、同步和验收由获权AI完成。Skill正式下载与客户端更新另验，不能据此宣布所有旧系统已经接入。
