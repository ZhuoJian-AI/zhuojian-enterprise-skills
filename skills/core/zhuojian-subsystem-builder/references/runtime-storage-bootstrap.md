# Runtime 存储初始化与自动保护

SaaS 负责平台云授权、企业 Runtime 绑定和受控证据展示；企业 Runtime 负责实际备份与恢复，Skill 规定开发与验收。负责人只提供自己服务器的访问授权和业务范围，不需要阿里云账号、Bucket、AccessKey 或平台 Token。服务器 root 不能凭空取得云权限，首次 Runtime 登记及存储预绑定由获权平台管理员 AI 完成。

## 平台先准备，企业 AI 自助接入

平台管理员在现有“服务器”的企业初始化入口，将已登记 Runtime 绑定到平台维护的存储档案，指定业务 OSS 是否启用及备份周期/本地保留数量。平台验证云授权后开放机器接口；该验证只说明存储权限可用，尚不代表企业数据已备份。业务范围固定为 `enterprises/<组织UUID>/<环境>/apps`，独立私有备份范围为 `enterprises/<组织UUID>/<环境>/backups`，组织及环境来自服务端 Runtime 身份。备份身份不允许删除云对象/版本，不向企业下发共享桶总身份。

企业 AI 使用本机既有 Runtime 登记 key，通过固定机器接口取得配置及两个独立用途的 STS；不展示、复制到聊天或要求用户操作云控制台。`business:null` 保留已有业务存储，不能改写旧桶、网关前缀或 release。备份目标与已有企业前缀不同则停止绑定，先明确迁移，不改旧恢复点。

部署 SaaS 机器接口及云档案后，企业 root 更新本次受影响的 Runtime helper 与随附备份工具，保留 Runtime 身份和私有配置，不重新签发 key：

```sh
python3 scripts/install_runtime_backup.py
zhuojian-storage-bootstrap configure
```

`configure` 验证已预绑定的身份与范围、企业外拒绝和备份版本控制，登记各系统的真实备份计划，安装固定 root 服务/定时器，触发首次在线备份与上报。普通负责人只给 root；这些命令与后续技术选择由开发 AI 完成。尚无平台绑定时明确报告未配置，保留本地和旧机外点，不假报成功。

已有经过验收的在线定时链不得被覆盖或重复运行。先核对实际 unit 与计划，再使用：

```sh
zhuojian-storage-bootstrap configure --preserve-existing-schedule --existing-backup-timer <已核实在线timer>
```

这只登记原定时器作状态查询，保留其日程、原计划与原缺失基线；初始化 AI 仍须实际验证其使用新版续期 provider 和既有备份路径。新安装的标准在线链仅替代已识别的旧 Runtime 停写 timer，不停止正在运行的业务容器。Scope 探针失败时保留原静态备份凭据；已有静态源身份继续兼容。

## STS 续期与网关

备份使用官方 SDK `ProviderAuth`，每次签名（含分片、回读及历史版本读取）检查有效期，临期通过同一机器身份续期；不把 15 分钟临时 Token 当长期密钥。主机还以受控服务定期刷新并上报。业务网关通过只挂载给网关的 business-only Unix socket 按需续期，socket 固定业务用途且校验主机 root peer，不接受用途、对象前缀、路径或命令。网关不取得 Runtime 登记 key 或备份身份，业务容器不挂载 socket。

业务租约写入专用私有目录，并以目录只读挂载给网关，使原子换文件能被 SDK 下次请求读到；不能依赖单文件 bind mount 自动看到新 inode。新业务网关仍需按 [文件存储](object-storage.md) 的安装、企业外拒绝、双应用隔离与重启探针完成真实验收，再设置未来新应用的默认后端。存储绑定本身不迁移既有附件或改变已有 release。

## 新系统必须取得自己的首次证明

启用平台存储保护后，受控发布钩子在健康代码提交落定后刷新该系统的 root-only 备份计划，并启动固定的 `zhuojian-initial-backup@<系统>.service`。默认模板的实际 SQLite 从固定数据挂载与文件魔数识别，并核对模板附件表所需字段；多个数据库候选、未知附件引用结构、外部库或 PG/MySQL 无已验收适配器时显示待补，由开发 AI 在已授权维护范围定位真实数据库、补齐专项适配并实测。不能调用任意项目命令冒充通用 root 备份适配器，也不能猜空目录表示无数据库。

新系统只有当前运行提交对应的数据库、文件、Git 备份完成精确云版本回读，并通过实际隔离恢复及引用核验，才通过首次登记保护验收。排队、计划 ready、上传返回成功或进程退出零均不足以放行。证明尚未通过时系统保持待补，不重做旧部署或停止其他系统；已上线旧系统的部分历史点继续保留。每个后续发布还要保留原有权限、数据边界与项目既定验收。

在线全量循环逐系统留结果。新增未计划系统或未知数据库记 `backup_plan_pending`，其他已验证计划继续，旧有效点不被失败任务抹掉。已有 root 手工审核计划的真实数据库位置、私有恢复配置和缺失引用基线保持；自动发现不覆盖它们。无适配器不等于已保护，开发 AI 不能据此结束承诺的交付。

## 自动进入管理员监控

初始化、备份完成及周期采样向固定 `storage-report` 机器接口上报有界元数据；平台认证 Runtime 并校验组织、环境、绑定 revision 和已登记应用集合，未登记的新本地系统保留本机，平台登记后自动出现。上报只含系统、任务、最近有效点、分项与恢复证据，不含云定位、对象键、密钥或文件正文。计划覆盖数量与实际备份/恢复结果分别显示，不能合成一个绿色状态。

当前失败任务与旧有效成功点独立；来源过期或断开不刷新原证明时间。恢复演练不回写生产库、不启动有外发行为的恢复应用；完整新机业务启动、跨库一致性及单企业生产切回仍分别验收。实际步骤与证据标准见 [备份覆盖与恢复验收](recovery-acceptance.md)。
