# 模块需求 · Skill

把一个说不清的想法，**问成一份开发拿着就能开工的模块需求文档**。

坐在对面的是不懂技术的业务负责人。这份 skill 全程**不要求他理解任何技术概念**，
产出的文档里**一个技术词都不出现**。

---

## 它在整条链路的哪一段

```
业务负责人有个想法
        │
        ▼
  ┌─────────────────┐
  │  模块需求（本库） │  只管「想清楚」
  │  · 判断要做哪几样 │
  │  · 逼问出真实需求 │
  │  · 讲清做成什么样 │
  │  · 成型为需求文档 │
  └────────┬────────┘
           │  交棒物 = 需求文档 + 原始材料 + 待定项清单
           ▼
  ┌──────────────────────────┐
  │ aifabei-subsystem-builder │  只管「做出来」
  │ 建模块 · 部署 · 接入平台   │  （另一个仓库，同事维护）
  └────────┬─────────────────┘
           ▼
     人工登记进主脑
```

**技术选型、怎么做、放在哪、怎么部署 —— 全部不在本库范围内。**
后一段的判断依据比这一段多，这里替它做决定就是添乱。

## 业务层级（决定了怎么问）

```
公司
└─ 多个业务模块          ← 交付、部署、迭代的单元
   └─ 一个或多个参与部门   ← 角色：牵头 / 协作 / 审批 / 只看
      └─ 页面、数据、能做的动作
```

三条推论：

1. **交付单元是模块，不是部门。** 别问「你们部门要什么」，
   要问「**这件事涉及哪几个部门，各自干什么**」
2. **参与部门永远是一份名单**，即使只有一个 —— 下游要求它是列表
3. **产物不只是看板。** 能看的面板 / 能查的页面 / 能动手的操作 / 提醒 / 定期报告，
   一个模块常常是几样的组合

## 两个载体，一个真相源

| 文件 | 给谁读 | 怎么来的 |
|---|---|---|
| `SKILL.md` + `references/` | Claude Code（按需读取） | **手写，改这里** |
| `AGENTS.md` | Codex（不支持分层，需要平铺全文） | **脚本生成，不要手改** |

改完 `SKILL.md` 或 `references/` 之后重跑：

```bash
python scripts/build_agents.py
```

手改 `AGENTS.md` 的话，下一个人重跑脚本就把你的改动覆盖掉了。

## 四条硬约束

其余规则都能按现场增删跳，这四条不行：

1. **一次只问一题** —— 他不是在填表，是在跟你聊
2. **形容词要砸成具体的东西** —— 「及时」「方便」「透明」都不算答案
3. **能给菜单就不要开放式问** —— 对不懂技术的人，开放式问题门槛高得多。
   开放式起头，菜单收口
4. **不许让他理解技术** —— 用什么技术、放在哪、怎么更新，那些是做的人该定的
